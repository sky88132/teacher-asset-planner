# Supabase 연결 전 점검 및 저장·보안 설계

점검일: 2026-11-07. 대상 코드: `02df042d7bdfe87c860f55e49806c2e4c56c3fe9` (`feat: add AI retirement prompt generator`). 이 문서는 설계 제안이며, Supabase 프로젝트 생성·연결, SQL 실행, 로그인 구현은 하지 않았다. 기존 화면·금융 계산·입력 데이터는 변경하지 않았다.

## 1. Git 및 검증 상태

- 로컬 `main`, 원격 추적 `origin/main`, GitHub의 `refs/heads/main`이 위 커밋으로 일치함을 확인했다. 기존 AI 기능 커밋을 다시 생성할 필요가 없다.
- 최초 미커밋 파일은 `next-env.d.ts` 하나였다. Next 개발 서버가 생성한 `.next/dev/types` 참조 변경이며 이번 문서 커밋에서 제외한다. 빌드가 바꾼 참조는 점검 전 상태로 복원한다.
- `npm run typecheck`: 성공. `npm test`: 129개 통과. `npm run test:browser`: 데스크톱·모바일 테스트 통과(`test-results/.last-run.json`: passed, 실패 목록 없음). `npm run build`: 성공.
- 추적 소스·문서·테스트·설정에서 비밀키, 개인키, 토큰, 개인정보 형태를 검사했다. 실제 비밀키·개인정보는 발견하지 않았다. 개인정보 형태의 일치는 AI 테스트 두 파일의 가상 이메일·이름·전화번호·계좌번호 사례와 IRP 자료·테스트의 공식 자료 URL 숫자였다. 패턴 검사만으로 모든 민감정보 부재를 보증할 수는 없다.
- 추적된 `.env`, PEM, KEY 파일은 없었다. 현재 Supabase SDK·인증·원격 저장·외부 AI API 호출은 없다. Node 테스트의 모듈 유형 경고는 실패가 아니다.
- 이 문서 작성 후 문서만 별도 커밋하고 원격 커밋 해시를 재확인한다. 최종 업로드 결과는 작업 완료 보고에서 기록한다.

## 3. 저장 범위와 원칙

현재 `src/lib/profile.ts`, `src/lib/finance/`의 `pension-input.ts`, `ktcu-input.ts`, `irp-input.ts`, `retirement-comparison-input.ts`, `cashflow-input.ts`, 그리고 `src/lib/ai/prompt-input.ts`의 입력 타입을 기준으로 한다. 실제 파일 분리는 구현 시 다시 확인한다.

저장의 원본은 **사용자 입력**이다. 결과는 같은 엔진으로 다시 계산한다. 공식 조회액의 `source: official`은 사용자가 직접 공식 조회값이라고 입력한 출처이지 앱의 진위 인증이 아니다. 저장 때문에 계산 신뢰도를 높이지 않는다.

- 금액 입력의 원문 문자열과 `won/manwon` 단위를 함께 보존한다. 빈 문자열, 0원, 유효하지 않은 편집 중 값은 서로 다르다. 저장된 미완성 초안이 계산을 활성화해서는 안 된다.
- 첫 단계는 버전이 있는 `input_json`을 원본으로 하고 서버 측 타입·크기 검증을 적용하는 방안을 권장한다. 검색용 정규화 컬럼이 필요해지면 서버가 원본에서 생성한다. 클라이언트가 서로 다른 두 금액을 저장하는 이중 원본 구조는 피한다.
- 유효 금액을 정규화할 때는 원 단위 정수, 기간은 월 단위 정수, 유효 날짜는 `date`, 비율은 정밀도가 정해진 `numeric`을 사용한다. TypeScript 계산으로 전달할 금액은 안전한 정수 범위 이내인지 검증한다. 잘못된 날짜 원문은 초안 JSON에만 남긴다.
- 공단 인정 재직개월과 달력상 기간은 별개다. 제도별 숨겨진 입력, 비활성 계좌, 비활성 사용자 시나리오도 삭제하지 않는다.
- 공적연금 월액은 적립금이 아니다. 공식 입력과 앱 추정은 별개이며 계좌 이체를 새로운 자산으로 만들지 않는다. 저장 계층은 기존 차단 조건과 합산 규칙을 바꾸지 않는다.
- 허용된 키만 받는 버전별 스키마, 문자열 길이·배열 수·JSON 크기 제한이 필요하다. 클라이언트 검증만 신뢰하지 않는다.

선택 확장 `plan_revisions`는 입력 스냅샷·프로필 revision·엔진 버전을 함께 보존하는 소유자별 변경 이력이다. 보존 기간과 삭제 동의가 결정된 후 도입한다. 첫 저장 단계에서 계산 결과 전체나 월별 현금흐름을 별도 저장할 필요는 없다.

현재 전역 계산 엔진 버전 체계는 없으므로 코드 SHA와 모듈 manifest부터 도입하는 것이 좋다. `saved_with_engine`은 저장 당시 버전이며 계산 실행·공식 검증 완료를 의미하지 않는다. 버전 등록부는 배포 측이 관리하고 클라이언트가 검증 완료 버전을 자칭할 수 없어야 한다. 엔진 변경 시 원본을 보존하고 재계산·변경 안내를 한다.

## 5. 개인정보와 AI 데이터

생년월일·임용일·금액·소득은 민감한 개인정보로 취급한다. 계산에 필요한 정확한 날짜의 저장과 AI에 익명화된 정보만 전달하는 것은 별개의 처리다. 저장 항목·목적·보존·삭제 방법을 사전 안내하고 동의를 받는다. 이름·학교명·이메일·계좌번호를 새 입력 항목으로 추가하지 않는다. 인증 이메일은 Auth가 관리하고 프로필에 복제하지 않는다.

AI `PromptWorkspace`의 `draft`, `original`, `generatedKey`, 추가 질문은 기본 원격 저장 대상에서 제외한다. 특히 `generatedKey`는 원본 상태의 JSON 지문이며 익명 식별자가 아니다. 현재 메모리 내 동작을 유지한다. 선택한 분석 종류·반올림 같은 비민감 설정만 향후 별도로 저장할 수 있다. 포함 정보 검토 동의·질문 검토 동의·정확한 날짜 허용은 새 세션에서 재확인한다.

자유 메모·금액 산정 가정에는 식별정보가 들어갈 수 있다. 업로드 전 안내·검토와 길이 제한이 필요하다. 저장하지 않을 항목은 명시하고 로컬 입력을 임의 삭제하지 않는다. 요청 본문·금융 JSON·AI 초안을 로그, 오류 추적, 분석 이벤트에 남기지 않는다.

## 6. RLS 및 접근권한 설계

Supabase는 객체 권한과 행 접근 정책을 함께 적용해야 한다. 노출되는 개인 테이블에는 RLS를 명시적으로 활성화한다. `auth.uid()`는 인증되지 않은 요청에서 null이며, UPDATE에는 기존 행의 `USING`과 새 행의 `WITH CHECK`, 조회 정책도 필요하다. [RLS 공식 문서](https://supabase.com/docs/guides/database/postgres/row-level-security), [API 보안](https://supabase.com/docs/guides/api/securing-your-api)

제안하는 소유자 조건 P는 `(select auth.uid()) IS NOT NULL AND (select auth.uid()) = user_id`이다. 다음 표는 정책 설계이지 실행한 SQL이 아니다.

| 대상 | SELECT | INSERT | UPDATE | DELETE |
| --- | --- | --- | --- | --- |
| 개인 데이터 테이블 전체 | authenticated, USING P | authenticated, WITH CHECK P | authenticated, USING P 및 WITH CHECK P | 첫 단계 권한·정책 없음 |
| `engine_releases` | authenticated에 비개인 메타데이터만 | 사용자 불허 | 사용자 불허 | 사용자 불허 |

설계상 추가 방어는 다음과 같다.

- 개인 자식의 `(plan_id,user_id)`가 부모 `(id,user_id)`를 함께 참조한다. 시나리오 조회값도 시나리오·계획·소유자를 함께 참조한다. A가 자신의 user_id로 B의 계획에 자식을 붙이는 요청을 막는다.
- 소유자·부모 식별자는 생성 후 변경하지 못하도록 DB 쓰기 권한 또는 제약을 설계한다. 소유자 열은 필수다. 검색용 인덱스는 소유자와 계획을 기준으로 둔다.
- 별도 `planner_api` 스키마를 노출 대상으로 제안하며 불필요한 객체에는 권한을 주지 않는다. anon 권한과 정책을 만들지 않고 익명 로그인도 사용하지 않는다. 수정 가능한 사용자 metadata를 권한 근거로 쓰지 않는다.
- 뷰·RPC·Realtime·Storage는 필요한 경우에만 추가한다. 뷰와 함수가 RLS를 우회하지 않도록 invoker 실행과 권한을 검토한다. 삭제는 별도 본인 확인·보존 정책 설계 후 허용하며 지금 데이터를 지우지 않는다.
- RLS는 프로젝트 관리자·DB 소유자·관리 키까지 제한하는 장치가 아니다. 브라우저는 publishable key와 사용자 세션만 사용한다. secret/service_role 키는 RLS를 우회할 수 있으므로 브라우저·저장소에 넣지 않는다. 일반 사용자 저장에 관리 키는 필요하지 않다. [API 키 공식 문서](https://supabase.com/docs/guides/getting-started/api-keys)

이 설계는 아직 DB에서 실행·검증되지 않았다. 프런트엔드에서 user_id를 필터링하는 것만으로 접근 제어를 대체할 수 없다.

## 7. 저장·복원과 충돌 방지

계획 전체 저장은 서버 검증과 단일 트랜잭션이 필요하다. 예상 revision과 현재 revision이 다르면 충돌을 알리고 자동 덮어쓰지 않는다. 프로필 revision도 함께 확인한다. 중복 요청은 요청 식별자로 처리하고 일부 자식만 저장되는 상황을 막는다. 현재 메모리 입력을 최초 클라우드 데이터로 자동 덮어쓰지 않는다.

구현 시 트랜잭션 RPC를 쓴다면 사용자 세션·invoker 권한을 유지한다. 직접 테이블 쓰기로 revision 검사를 우회할 수 없도록 권한·DB 제약·갱신 절차를 함께 검토해야 한다. 버전·수정 시각은 신뢰된 DB/배포 경로가 설정한다. 구버전 입력의 변환은 테스트된 명시적 마이그레이션으로 처리하며 원본을 보존한다.

로그아웃·사용자 변경 시 메모리와 캐시는 사용자별로 분리하여 다른 사용자의 데이터를 표시하지 않도록 한다. 기존 입력의 업로드 여부는 사용자에게 명확히 안내한다. 자동 저장·실패 재시도·오프라인 동작도 실제 연결 단계에서 정의한다.

## 8. 연결 전 필수 보안 테스트

아래 테스트는 아직 미실행이다. 현재 앱 테스트 통과와 구분한다. 가상 사용자 A/B와 가상 금액만 사용한다.

1. 미로그인·만료 세션 접근 거부, A/B 교차 조회·수정·삽입·upsert 차단.
2. user_id 위조·변경, 다른 소유자 계획/시나리오 참조 차단.
3. 모든 개인 테이블·뷰·RPC에 동일한 격리 적용, 허용되지 않은 삭제 거부.
4. 조회·수정 정책이 다른 사용자 행을 숨길 때 오류 없이 0행이 반환될 수도 있으므로 실제 데이터 불변도 확인.
5. 빈 값/0/원·만원/미완성 날짜/비활성 입력의 저장·복원 일치.
6. 동시 수정 충돌, 전체 저장 롤백, 재시도 중복 방지, 입력 버전 변환·엔진 변경.
7. AI 원문·개인 메모·금융 값의 로그 유출 방지, 계정 전환 시 캐시 분리.
8. 백업 복원 및 향후 본인 삭제 정책 검증. 운영 데이터 사용 전 모두 통과해야 한다.

## 9. 필요한 사용자 설정과 후속 파일

**이번 단계에서 설정을 요청하거나 프로젝트를 만들지 않는다.** 다음 연결 단계의 준비 목록이다.

- 프로젝트 소유 계정·지역·개발/운영 분리, 개인정보 처리 및 보존·백업 정책 결정.
- 로그인 방식 선택, 익명 로그인 비활성화, 개발·운영의 정확한 리다이렉트 URL 허용 목록 결정. 실제 콜백 경로는 구현 후 맞춘다.
- 향후 공개 환경변수는 `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`를 제안한다. 실제 값은 추적하지 않는 `.env.local`에 설정한다. 비밀키를 채팅이나 GitHub에 올리지 않는다.
- 스키마 노출·권한·RLS 마이그레이션을 검토하고 위 교차 사용자 테스트를 마친 뒤 연결한다. SSR 구현 시 현재 Next 설치 문서와 [Supabase Next 클라이언트 안내](https://supabase.com/docs/guides/auth/server-side/creating-a-client?queryGroups=framework&framework=nextjs)를 다시 확인한다.

이번 변경 파일은 이 문서뿐이다. 후속 단계에서 예상하는 파일은 DB 설계·마이그레이션 파일, 입력 직렬화/서버 검증/스키마 버전 모듈, 소유권·저장복원 테스트다. 실제 연결 승인 이후에만 Supabase 클라이언트, 환경변수 예시, 인증/세션 처리, 저장 상태 UI 및 관련 의존성을 추가한다. 현재 금융 계산 모듈은 변경 대상이 아니다.
